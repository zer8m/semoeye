# 다면 검토 서비스 설계서

작성일: 2026-09-14 · 마감: 3일 내 · 제출물: 배포 URL + 기획서(PRD)

서비스명: **세모눈 (semoeye)** — 의심할 때 뜨는 눈초리. 2026-09-15 확정.

## 1. 문제 정의

- 기획안·아이디어를 남에게 보이기 전 스스로 검토하면 맹점이 안 보인다.
- AI에게 검토를 맡기면 대체로 긍정 평가만 돌아온다(아부 문제).
- 주변인 피드백은 시간·성의 한계가 있다. 공모전 참가자, 창업 준비생, 기획자, 학생은 적절한 검토자를 구하기 어렵다.

## 2. 해결 컨셉

아이디어를 붙여넣으면 **반대자가 반드시 포함된 3~4명의 AI 검토진**이 각자 고정된 질문으로 독립 검토하고, 합의가 아니라 **갈린 지점과 판정(진행/보류/폐기)**을 돌려준다. 판정에 불복하면 검토진과 무제한 토론할 수 있지만, **새 근거 없이는 판정이 바뀌지 않는다.**

차별점:

1. 전원 찬성이면 검토 실패로 간주하고 재작성한다 — 아부하는 AI의 구조적 반전.
2. "폐기"로 끝나지 않는다 — 항상 "이 판정을 뒤집을 관찰 하나"를 제시해 다음 행동으로 연결.
3. 말발로는 판정이 안 바뀐다 — 새 사실·데이터·관찰을 가져와야 재심된다.
4. 아이디어는 본인 계정에만 격리 저장된다 — Supabase RLS(Row Level Security)로 다른 사용자·운영자가 열람할 수 없음을 아키텍처로 보장. 로그인 없이도 검토는 가능하며, 저장·기록은 로그인 시에만 동작한다.

## 3. 예선 스킬 활용 원칙 (배점 30점 핵심)

FAQ 기준: "그대로 호출"이 원칙, 서비스화 확장은 허용하되 PRD 스킬 매핑에 기재.

- **불변 코어**: 예선 스킬 `multi-angle-review`의 지시문 전체(검토자 명단·배정 규칙·검토 규칙·출력 포맷·절대 규칙·예시)를 무수정으로 `skill/multi-angle-review.md`에 두고, 서버가 이 파일을 읽어 시스템 프롬프트의 코어로 사용한다. "그대로 호출"을 코드 레벨에서 증명.
- **확장 블록**: 코어 뒤에 별도 블록으로만 추가 지시를 주입한다.
  1. 토론 모드 규칙(§6)
  2. 검토자 지목 응답 규칙(§6)
  3. 웹 UI 파싱용 출력 구분자(출력 내용·포맷은 스킬 원문 그대로, 구분자만 추가)
- **PRD 스킬 매핑 표**: 기획서에 "스킬 원문 조항 → 서비스 기능" 매핑과 확장 내역을 표로 기재한다.

심사 추적 경로: 기획서 매핑 표 → 리포지토리의 스킬 원문 파일 → 실제 서비스 출력.

## 4. 화면 흐름 (PersonaFlight UI 재사용)

기존 PersonaFlight UI(비디오 히어로 랜딩, 원형 캐러셀, 페르소나 카드 그리드, 세션 화면, 단계 레일)를 골격 그대로 재사용하고 콘텐츠와 로직만 교체한다.

1. **랜딩**: 비디오 히어로 유지, 문구·CTA 교체.
2. **로그인/회원가입**: 기존 폼 UI에 Supabase Auth(이메일+비밀번호) 연결. 로그인 없이도 검토 가능, 저장은 로그인 시에만.
3. **안건 입력** (구 프로젝트 선택): 좌측에 안건 텍스트 입력창, 원형 캐러셀에 안건 유형 4종(만들지 말지 / 방법 검토 / 공모전 제출물 / 돈·일정 — 미선택 시 자동 감지).
4. **검토자 화면** (구 페르소나 피커): 스킬의 검토자 8명을 아바타 카드로 소개, 말풍선에 각자의 고정 첫 질문. 기본은 자동 배정으로 바로 시작, 카드 선택 시 수동 지정(스킬의 "지정했으면 그대로 쓴다" 조항).
5. **검토 리포트 + 토론** (구 피드백 세션): 로딩 연출 재사용 → 검토자 카드 스트리밍 → 반박(A→B) → 모인/갈린 지점 → 판정 배너(진행/보류/폐기 + 뒤집을 조건) → 하단 토론 입력창. 검토자 지목(@반대자 등) 시 해당 페르소나가 1:1 응답. 판정 변경 시 배너 명시.
6. **내 기록**: 로그인 사용자의 과거 세션 목록(Supabase에서 로드) — 열면 리포트·토론을 이어서 진행 가능.

## 5. 기술 설계

스택: Next.js(App Router) + Vercel + OpenAI 호환 LLM 게이트웨이(스트리밍, `LLM_BASE_URL`·`LLM_MODEL` 환경 변수로 교체 가능) + Supabase(Auth + Postgres, RLS).

```
├─ skill/multi-angle-review.md      예선 스킬 원문, 무수정
├─ src/app/
│  ├─ page.tsx                      랜딩
│  ├─ login/ · signup/              Supabase Auth
│  ├─ review/page.tsx               안건 입력
│  ├─ review/panel/page.tsx         검토자 소개·지정
│  ├─ review/session/page.tsx       리포트 + 토론
│  └─ api/review/route.ts           유일한 API (스트리밍 프록시)
└─ src/lib/
   ├─ prompt.ts                     [스킬 원문] + [확장 블록] 조립
   ├─ parser.ts                     스트리밍 마크다운 → 카드/판정 파싱
   └─ supabase.ts                   클라이언트 + 세션 저장/로드
```

- `/api/review`는 stateless 프록시: 브라우저가 `messages` 배열(대화 히스토리 전체)을 매 요청에 들려 보내고, 서버는 시스템 프롬프트를 붙여 LLM 게이트웨이에 중계 후 스트림을 그대로 흘린다.
  - 1차 검토 = 안건 1개 메시지 → 전체 리포트
  - 토론 = 기존 히스토리 + 새 메시지 → 이어서 응답
- 저장: 클라이언트가 Supabase에 직접 기록(anon key + RLS). `reviews` 테이블 — id, user_id, title, agenda, messages(jsonb), verdict, verdict_reason, updated_at. RLS 정책: `user_id = auth.uid()`인 행만 select/insert/update/delete.
- 파싱: 스킬 출력의 고정 포맷(`## 검토`, `## 반박`, `판정:` 등)을 정규식 섹션 파서로 분해해 카드 UI로 렌더. 파싱 실패 시 마크다운 원문 그대로 표시하는 폴백.
- 에러 처리: API 실패·쿼터 초과 시 재시도 버튼. 진행 중 히스토리는 브라우저 메모리에 있으므로 유실 없음.
- API 키는 서버 환경변수로만 보관. 요청 크기 상한(안건 최대 길이)과 히스토리 길이 상한을 둔다.

## 6. 토론 게이트 (확장 블록 규칙)

- 사용자 반박에 새 사실·데이터·관찰이 포함될 때만 판정 변경을 허용한다. 단순 반박·감정 호소·같은 주장의 반복에는 "판정 유지 — 근거 재확인"으로 응답한다.
- 판정이 바뀌면 응답 첫 줄에 `[판정 변경] 보류→진행 — 사유` 형식으로 선언한다. UI는 이를 배너로 표시하고 localStorage 기록을 갱신한다.
- 검토자 지목 시 해당 검토자의 고정 질문·판단 근거·기존 발언과 일관된 페르소나로만 응답한다. 지목되지 않은 검토자는 발언하지 않는다.

## 7. 제출물 구성

1. 배포 URL (Vercel)
2. 기획서(PRD) — 채점표 순서대로: 문제 정의(25) / 스킬 매핑 표(30) / 사용 흐름·사용성(15) / 차별점·확장성(20) / 발표 시나리오 1페이지(10)

## 8. 3일 계획

- 1일차: 엔진 + 파서 — 안건 입력→검토 리포트까지 끝까지 관통
- 2일차: 토론 모드 + 지목 응답 + 판정 변경 게이트 + 내 기록
- 3일차: UI 폴리시, 에러 처리, PRD 작성, 배포 점검

## 9. 범위 제외 (이번 버전에서 안 함)

- 파일(PDF/PPT) 업로드, 결제, 다국어, 검토자 커스텀 편집, 소셜 로그인, 세션 공유 링크.

## 10. 제작 규칙

- 코드 주석을 달지 않는다.
- 커밋 메시지·코드·문서 어디에도 AI 도구 사용 흔적을 남기지 않는다.
