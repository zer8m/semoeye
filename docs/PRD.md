# 세모눈 — 다면 검토 서비스 기획서

기획안·아이디어를 넣으면 반대자가 반드시 포함된 AI 검토진이 각자의 고정 질문으로 따져 묻고, 모인 지점과 갈린 지점을 가른 뒤 진행·보류·폐기를 판정하는 서비스.

---

## 1. 문제 정의

### 1-1. 문제

기획안이나 아이디어를 다른 사람에게 보여주기 전, 스스로 검토하면 자신의 맹점은 보이지 않는다. 그렇다고 검토를 맡길 곳도 마땅치 않다.

| 검토 방법 | 실패 이유 |
| --- | --- |
| 스스로 검토 | 자기 아이디어의 맹점은 자기 눈에 안 보인다 |
| 일반 AI에게 검토 요청 | 대체로 긍정적인 평가만 돌아온다 — 사용자 비위를 맞추는 방향으로 답한다 |
| 주변 사람에게 요청 | 시간을 들여 꼼꼼히 검토해주기 어렵고, 관계 때문에 쓴소리를 삼간다 |

특히 공모전 참가자, 창업 준비생, 기획자, 학생은 아이디어를 객관적으로 검증받고 싶어도 적절한 검토자를 구하기 어렵다. 결과적으로 검증 없이 제출·실행하고, 시행착오 비용을 사후에 치른다.

### 1-2. 해결

한 명의 AI가 총평을 주는 대신, **서로 다른 고정 관점을 가진 3~4명의 AI 검토자가 독립적으로 평가**하고 그 결과를 구조적으로 합친다.

- 각 검토자는 고정된 첫 질문과 판단 근거 하나를 가지며, 바뀌지 않는다 — 관점이 섞이지 않는다.
- 검토자 중 한 명(반대자)은 **항상 이 안이 실패하는 쪽에 서 있다** — 아부가 구조적으로 불가능하다.
- 의견이 모인 지점과 갈린 지점을 분리해 보여주고, 진행/보류/폐기를 판정한다.
- 판정이 "폐기"여도 끝이 아니다 — **이 판정을 뒤집을 관찰 하나**를 반드시 제시해 다음 행동으로 연결한다.
- 판정에 불복하면 검토진과 무제한 토론할 수 있다. 단, **새로운 사실·근거가 제시될 때만 판정이 바뀐다.** 같은 주장의 반복이나 감정 호소로는 바뀌지 않는다.

## 2. 예선 스킬 매핑

이 서비스의 검토 엔진은 예선 제출 스킬 `multi-angle-review`(다면 검토 — 반대자 포함 판정)다. 스킬 지시문 전체를 **한 글자도 수정하지 않고** 리포지토리의 `skill/multi-angle-review.md`에 두고, 서버가 이 파일을 읽어 시스템 프롬프트의 코어로 사용한다. 서비스화에 필요한 규칙은 원문 뒤에 별도 확장 블록으로만 추가한다(`src/lib/prompt.ts`).

### 2-1. 스킬 원문 → 서비스 기능 매핑

| 스킬 원문 조항 | 서비스에서의 구현 |
| --- | --- |
| 검토자 명단 (8인, 고정 질문·판단 근거) | 검토진 화면의 8개 카드 — 말풍선에 고정 첫 질문, 카드에 판단 근거 표기 |
| "사용자가 검토자를 지정했으면 그대로 쓴다" | 검토진 화면에서 검토자 직접 지정(최대 3명 + 반대자) → `[지정 검토자: …]` 태그로 전달 |
| 배정 규칙 (안건 단계 4종 → 검토자 조합) | 안건 입력 화면의 단계 캐러셀. 미선택 시 자동 감지 |
| "[반대자] 언제나 포함한다. 예외 없다." | UI에서 반대자 카드는 지정 해제 불가 — "예외 없이 포함됩니다" |
| 출력 포맷 (검토/반박/모인·갈린 지점/판정) | 리포트 화면의 섹션 파서(`src/lib/parser.ts`)가 이 포맷을 그대로 카드·배너로 렌더 |
| "반박을 정확히 한 번 넣는다" | 리포트의 반박([A] → [B]) 강조 블록 |
| "아무도 말하지 않은 것" | 리포트 하단의 반전 색 강조 카드 |
| 판정 + 뒤집을 조건·관찰 | 판정 배너(진행🟢/보류🟡/폐기🔴)와 조건 목록 |
| "전원 찬성으로 끝나면 검토 실패" | 시스템 프롬프트에 그대로 유지 — 모델이 재작성 |
| "모르면 확인 안 됨이라 쓴다" | 시스템 프롬프트에 그대로 유지, 토론 규칙에도 재명시 |

### 2-2. 확장 내역 (서비스화를 위해 추가한 것)

| 확장 | 이유 |
| --- | --- |
| 입력 태그 규칙(`[안건 단계: …]`, `[지정 검토자: …]`) | 웹 UI의 선택값을 스킬의 배정 규칙에 연결 |
| 토론 규칙 — 새 근거 게이트 | 첫 리포트 이후의 대화에서 "새로운 사실·근거가 있을 때만 판정 변경"을 강제. 응답 첫 줄에 `[판정 변경]`/`[판정 유지]` 선언 |
| 검토자 지목 응답(`[지목: 검토자명]`) | 특정 검토자와 1:1 토론. 해당 검토자의 고정 질문·판단 근거·기존 발언과 일관되게 응답 |
| 근거 분리 입력(`[근거]` 블록) | 토론 입력에서 주장과 근거를 별도 필드로 받아, "근거가 있어야 판정이 바뀐다"는 규칙을 입력 단계부터 드러냄 |
| 인정/불인정 근거 구분 응답 | 재검토 후 "인정한 근거"와 "근거로 보지 않은 것"을 나눠 명시 — 판정 유지가 자의적이지 않음을 보여줌 |
| 근거 평가 4단계 서술 | 반박·근거를 받으면 요약 → 기존 근거와 대조 → 인정 여부와 이유 → 판정 영향 순으로 과정을 드러내며 평가 — 결론만 던지지 않음 |
| 상세 검토(`[상세: 검토자명]`) | 리포트의 검토자 카드를 누르면 그 검토자가 첫 검토를 8~15줄로 확장 — 주목한 대목 인용, 판단 근거 적용 과정, 성립 조건, 실패 경로, 확인할 관찰 |
| 토론 응답 길이 제한(15줄) | 대화 품질 유지 |
| 검토자별 고정 루브릭 채점 | 검토자마다 3항목×5점 채점 기준을 고정해 객관성 확보. 근거 없는 항목은 낮게 매기도록 지시 |
| 위험도 평가 | 판정에 더해 기준 적합성·주제 중복·구현 난이도 3축 위험도(낮음/중간/높음)를 산출 |
| 유사도 기반 자동 배정 | 안건과 검토자 프로필의 벡터 유사도를 계산해 상대 적합도 60% 이상 검토자만 조합(반대자 상시 포함). 배정 결과는 스킬의 "지정했으면 그대로 쓴다" 조항으로 전달 |
| 문서 텍스트 추출 | PDF·Word(.docx)·PPT(.pptx)·한글(.hwp/.hwpx)·텍스트 파일에서 브라우저 내 추출로 안건·근거 입력. 브라우저 추출이 실패한 스캔본 등은 docling 전처리 서버(`DOCLING_URL`)로 자동 위임하는 2단 구조 |

스킬 원문은 수정하지 않았고, 위 확장은 전부 원문 뒤에 붙는 별도 블록이다. 심사 시 `skill/multi-angle-review.md`(원문) → `src/lib/prompt.ts`(확장 블록) → 실제 서비스 출력 순으로 추적할 수 있다.

## 3. 사용 흐름·사용성

### 3-1. 화면 흐름

```
랜딩 → 안건 입력 (붙여넣기 + 단계 선택) → 검토진 확인·지정 → 검토 리포트 → 토론 → (로그인 시) 내 기록
```

- **처음 방문자 기준 클릭 3번**이면 판정까지 도달한다: 검토 시작하기 → (안건 붙여넣기) 검토진 확인하기 → 자동 배정으로 검토 시작.
- 로그인 없이 전 기능(검토·토론)을 쓸 수 있다. 로그인은 기록 저장이 필요할 때만.
- 검토 진행은 실시간 스트리밍 — 검토자 카드가 순서대로 채워지는 것을 보면서 기다린다.
- 판정·토론 중 오류가 나도 진행 중이던 대화는 브라우저에 있어 유실되지 않고, 재시도 버튼 하나로 복구한다.
- **LLM 지연·장애 폴백**: 25초 안에 응답이 시작되지 않으면, 미리 저장해 둔 검토 예시 중 가장 유사한 것을 대신 보여준다. 안건 텍스트를 256차원 벡터로 변환해 pgvector 코사인 유사도로 검색하고, 키워드 기반 카테고리가 같은 행을 우선한다(카테고리 분류 + 벡터 유사도 결합). 임베딩을 외부 API 없이 자체 계산하므로 LLM이 완전히 죽어도 폴백은 동작하며, 화면에는 "유사 안건의 저장된 검토 예시"임을 명시해 사용자를 속이지 않는다.

### 3-2. 데이터·개인정보

- 저장은 **로그인 사용자의 선택적 혜택**이다. 저장 시 Supabase Row Level Security로 사용자별 행 단위 격리 — 다른 사용자·운영자가 열람할 수 없음을 정책(DB 레벨)으로 보장한다.
- 비로그인 사용 시 서버에 아무것도 남지 않는다.
- 기록 삭제는 내 기록 화면에서 즉시 가능하다.

## 4. 독창성·확장성

### 4-1. 사용 전후

| 사용 전 | 사용 후 |
| --- | --- |
| "좋은 아이디어네요"라는 AI 칭찬 | 누가 무엇에 반대했는지, 어디서 갈렸는지가 남는다 |
| 막연한 불안("뭔가 놓친 것 같은데") | "아무도 말하지 않은 것" — 전원이 놓친 위험 1개가 명시된다 |
| 검토 결과가 결론 없이 흩어짐 | 진행/보류/폐기 판정 + 뒤집을 관찰 1개 → 다음 행동이 정해진다 |
| 반박하면 AI가 바로 수긍 | 새 근거 없이는 판정 유지 — 검증의 신뢰성이 유지된다 |

### 4-2. 문제 해결 방식의 새로움

1. **아부 문제를 프롬프트가 아니라 구조로 해결** — "비판적으로 봐줘"라는 요청은 한 번의 대화로 무력화되지만, 실패에 베팅한 반대자를 명단에 상주시키고 "전원 찬성 = 검토 실패" 규칙을 두면 구조적으로 무력화가 불가능하다.
2. **판정 변경에 증거 기준을 도입** — 대화형 AI의 "사용자가 우기면 수긍하는" 특성을 새 근거 게이트로 차단. 판정 변경은 `[판정 변경]` 선언과 사유가 남는 명시적 이벤트다.
3. **폐기가 막다른 길이 아님** — 모든 판정에 "뒤집을 관찰"이 붙어, 부정적 결과가 다음 검증 행동으로 이어진다.

### 4-3. 확장 방향

- 검토자 커스텀: 조직 고유의 관점(브랜드 담당, 법무 등)을 검토자로 추가
- 팀 공유: 판정 리포트를 링크로 공유, 팀원이 토론에 참여
- 문서 업로드: PDF·슬라이드를 안건으로 직접 입력
- 재검토 추적: 같은 안건의 판정 변화 이력(v1 폐기 → v2 보류 → v3 진행)을 타임라인으로

## 5. 발표 시나리오 (3분)

1. **(30초) 문제** — "아이디어를 AI에게 검토받아본 적 있으시죠. 뭐라고 하던가요? '좋은 아이디어네요.' 저희는 그 칭찬이 문제라고 봤습니다."
2. **(30초) 구조 소개** — 검토진 화면을 띄우고: 8명의 검토자, 각자 고정 질문 하나. 그리고 반대자 — "이 안이 실패하는 쪽에 걸었습니다. 예외 없이 참여합니다."
3. **(60초) 라이브 데모** — 실제 안건 입력 → 검토 스트리밍 → 갈린 지점 → 판정 "보류" + 확인할 것 하나.
4. **(45초) 토론 게이트** — 판정에 그냥 반박: "판정 유지". 새 근거(설문 수치)를 제시: "[판정 변경] 보류 → 진행". — "말발이 아니라 근거가 판정을 바꿉니다."
5. **(15초) 마무리** — "세모눈은 예선 스킬 multi-angle-review를 한 글자도 바꾸지 않고 엔진으로 씁니다. 스킬이 곧 서비스입니다."
